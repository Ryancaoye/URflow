# URFlow 开发规范

用户于 2026-10-29 确认。今后 URFlow 新功能和独立代码修复默认采用此流程；与当前任务的明确要求冲突时，以用户要求为准。

## 核心约定

保留稳定版，在独立开发目录实现功能，分小步验证和保存，正式发版再统一合并、更新版本与打包。

- 分支：另一条开发路线。
- worktree：把这条分支放到另一个目录，稳定目录与开发目录可以同时保留。
- commit：可比较和回退的版本存档点。
- tag：标记一个明确的正式版本；不需要每次编辑都打标签。

## 1. 明确要做什么

先用简单文字记录：

- 想解决的问题和功能入口。
- 用户怎样操作，预期看到什么结果。
- 什么结果算通过，以及可能受影响的旧功能。

结合现有实现形成具体方案；复杂功能拆成几个可独立验证的小阶段。

## 2. 核对并保存当前状态

检查分支、HEAD、Git 状态、已有 worktree 和当前稳定版本；需要更新远程状态时先保护本地改动。不能访问远程时明确记录本地核对范围。

逐项确认未提交改动的归属，保留文档、代码和新文件。相关已完成内容可单独提交，未完成内容可使用明确标记的 WIP 提交或核验过的独立备份；不为了清空工作区丢弃内容，也不把无关改动一起提交。

开发起点使用本次确认的稳定状态，不永远固定在 v1.0.3。

## 3. 建立或复用独立开发目录

每个独立功能或代码修复默认建立独立分支和 worktree，例如 feature/<功能短名> 或 fix/<问题短名>。具体名称与目录按任务确定；已有合适的开发目录应复用，同一功能后续调整继续在原分支进行。

原源码目录保留。worktree 不会自动带上未提交文件；必须确认功能所需内容已妥善保存，并确认开发目录中存在 AGENTS.md 和本规范。规范尚未提交时，可复制这两份文件到开发目录并核对一致，后续按相关提交保存。

在测试用 Unity 工程中加载开发目录的插件，并确认实际加载路径，避免试到旧版或把使用中的稳定版直接替换掉。

纯文档和流程规范修改可以在合适的现有目录完成，无需每次另建 worktree。

## 4. 分小步实现和保存

一次围绕一个目标修改，避免同时调整无关界面、曲线算法和预设逻辑。保留 Unity .meta 文件及 GUID。

每完成一个能独立验证的代码功能节点，就核对差异并提交一次。提交只包含该节点的相关文件；不要求每改几行就提交，也不把 git add 当备份。临时停顿可保存为 WIP，stash 用于短期切换，不作为长期存档。

使用已经确认的 Git 提交身份。身份缺失时报告并等待必要信息，不擅自替用户设置姓名和邮箱。

## 5. 验证新功能及受影响的旧功能

根据改动完成适当的静态检查、编译和 Unity 操作验证。核心回归候选包括：

- READ → 编辑 → APPLY 的结果和动画预览。
- 预设选择、保存、收藏及导入导出。
- Undo / Redo、Dopesheet / Curves 切换。
- 曲线保护及关键帧增删、移动；仅在本次改动可能影响时扩展覆盖范围。

记录通过、失败和未执行的检查，以及 Unity 版本、测试场景和实际加载的开发版本。静态阅读推测、实际复现、修复和运行验证必须分开描述。未做 Unity 实测的内容不能称为完整验收。

## 6. 交付功能与正式发版

功能完成时记录分支、开发目录、基线提交、阶段提交、改动说明和验证结果；待验证部分继续明确保留。

功能开发完成不自动代表要发布。合并、推送和正式发布按当次授权范围执行；已经明确授权的步骤不重复询问。

正式发版时：

1. 将通过验收的功能合入正式分支，并确认发布范围。
2. 同步 version.txt、package.json 的 version、URflowWindow.VERSION 和 CHANGELOG.md。
3. 更新受影响的 README、中文指南及 Word 内容；需要重新生成 Word 时检查排版。
4. 保存干净的发布提交，打 vX.Y.Z 标签；在授权范围内推送正式分支和标签。
5. 从对应发布版本生成 URflow_vX.Y.Z.zip，保留 .meta 和图标，核对安装包与标签对应。
6. 同步整理目录中的安装包、使用说明和开发记录。

每个正式版本都应能通过提交和标签找回。安装包用于安装和分发，不能代替 Git 版本历史；历史版本保留，不覆盖为同名的新内容。
